# TDD Rules

⚠️ **이 규칙은 Rigid — 상황에 맞게 변형하지 마라**

## 1. 적용 기준 구분

### ✅ TDD 반드시 적용

- **비즈니스 로직**: 상태 관리, 계산, 조건문, 데이터 변환
- **API 엔드포인트**: 요청 처리, 응답 형식, 에러 처리
- **유틸 함수**: 재사용 가능한 순수 함수 (parsing, validation, formatting)
- **버그 수정**: 버그를 재현하는 테스트 작성 후 수정
- **복잡한 Hook**: 상태 로직, 사이드 이펙트 조율

### ❌ TDD 불필요

- **타입 정의**: interface, type, enum 선언
- **설정 파일**: tsconfig, vite.config, eslintrc 등
- **순수 UI 컴포넌트**: 단순 렌더링만 하는 presentational component (snapshot test는 불필요)
- **SQL/데이터베이스 스키마**: DB는 migration으로 관리
- **스타일**: CSS, inline styles (visual regression 필요 시 별도 도구)

## 2. RED-GREEN-REFACTOR 사이클

### 🔴 RED: 하나의 동작만 테스트하기

1. **한 번에 하나의 동작**만 구현
   - "버튼을 클릭하면 X 한다" = 1개 테스트
   - "API 호출이 성공하고 데이터를 파싱한다" = 분리된 2개 테스트

2. **테스트 작성 후 반드시 실행해서 실패 확인**
   - `bun run test` 또는 `npm test` 실행
   - 실패해야만 진행 (실패하지 않으면 테스트가 작동하지 않는 것)
   - **실패 이유가 "기능이 구현되지 않음"이어야 함**
     - ❌ "파일을 찾을 수 없음" → 파일 생성 후 진행
     - ❌ "함수가 정의되지 않음" → 함수 스텁 생성 후 진행

3. 테스트를 충분히 구체적으로 작성
   - assertion은 명확하게
   - 입력과 기대값을 명시

### 🟢 GREEN: 최소한의 코드로 통과시키기

1. **YAGNI 원칙 적용** (You Ain't Gonna Need It)
   - 테스트를 통과시키는 최소 코드만 작성
   - 미래를 대비한 코드 추가 금지
   - "나중에 필요할 것 같은" 기능 금지

2. **모든 테스트 통과 확인**
   - 신규 테스트: 통과
   - 기존 테스트: 모두 통과 (회귀 없음)

3. 예제 (O vs X)
   ```typescript
   // ❌ 과도한 구현 (GREEN에서는 금지)
   function add(a, b) {
     if (typeof a !== 'number' || typeof b !== 'number') {
       throw new Error('숫자만 입력 가능');
     }
     return a + b;
   }

   // ✅ 최소 구현 (GREEN에서 이 정도)
   function add(a, b) {
     return a + b;
   }
   // → 검증 로직은 다른 테스트에서 추가
   ```

### 🟡 REFACTOR: 코드 정리 (GREEN 유지)

1. **할 수 있는 작업**
   - 중복 제거 (DRY)
   - 변수명/함수명 개선
   - 헬퍼 함수 추출
   - 간단한 리팩토링

2. **금지 사항**
   - 새로운 동작 추가 금지
   - 테스트 추가 금지 (이미 GREEN인 상태에서)

3. 검증: `bun run test` 모두 통과해야 함

### 반복

다음 동작에 대해 RED로 돌아가기 → 새로운 테스트 작성

## 3. 삭제 강제 규칙

### 테스트 전에 프로덕션 코드를 작성했다면?

1. **그 코드를 즉시 삭제하라**
2. RED부터 재시작
3. "참고용"으로 남기는 것도 금지
   - 참고가 필요하면 테스트에 주석으로 남길 것

**이유**: 이미 작성된 코드에 맞춰 테스트를 작성하면 "테스트가 코드를 검증하는" 대신 "코드가 테스트를 작성하게" 됨 → TDD의 이점 상실

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순할수록 테스트 작성도 빠르다. 테스트가 문서 역할을 한다. |
| "나중에 테스트 추가하겠다" | "나중에"는 오지 않는다. 지금 당장 테스트 먼저 작성. |
| "시간이 없다" | TDD가 더 빠르다. 테스트 없이 진행하면 디버깅과 리팩토링에 2배 이상의 시간 소요. |
| "삭제하면 낭비다" | 이미 작성된 프로덕션 코드는 낭비가 아니라 **기술 부채**. 삭제하는 게 더 빠르다. |
| "프로토타입이라 테스트 불필요" | 프로토타입도 TDD로 작성하면 프로덕션 코드로 승격이 쉽다. 나중에 다시 작성하는 게 낭비다. |
| "이미 수동 테스트했으니 OK" | 수동 테스트는 반복 불가능하고 검증되지 않는다. 자동 테스트 필수. |

## 5. 프로젝트별 규칙 우선 조항

- **이 파일(`TDD_RULES.md`)은 기본값(fallback)**
- 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 규칙이 명시되어 있으면 **그것을 우선**
- 충돌 발생 시: 프로젝트 문서 > TDD_RULES.md 순서

---

## 6. 체크리스트 (진행 중)

- [ ] RED: 테스트 작성 → 실패 확인 (기능 미구현 이유로)
- [ ] GREEN: 최소 코드 작성 → 모든 테스트 통과 확인
- [ ] REFACTOR: 중복 제거/이름 개선 → GREEN 유지
- [ ] 반복: 다음 동작에 대해 RED로 복귀
